# s-router-prod Cutover Plan

## Purpose

Replace the current legacy router setup with a dedicated `s-router-prod` router target generated by the `network-*` pipeline.

This document is scoped to the production replacement path. Lab, HAT, SIT, and switch-access scaffolding are out of scope for the production router contract.

## Current Baseline

The relevant production root input pins are declared explicitly in `flake.nix`.
They currently match the upstream `origin/main` heads of the production
router-chain repositories:


`network-labs` provides migration and conformance material, but is not

from `prod-network/s-router-prod` and does not select a lab topology.

`network-renderer-nixos-prod` follows the prod-pinned control-plane,
forwarding-model, and NixOS compiler inputs. `network-control-plane-model-prod`
follows the prod-pinned forwarding-model input, and
`network-forwarding-model-prod` follows the prod-pinned compiler input. This
keeps `s-router-prod` on one explicit production graph without making any lab

## Production Origin Pins

For the legacy replacement cutover, keep commit pins in `flake.nix` for the
production router chain. The pins should be advanced intentionally to current
origin commits, then committed together with the rendered-prod changes they are
meant to support.

The goal is to make it obvious from `flake.nix` that `s-router-prod` depends on a fixed router-chain revision set and must not move just because upstream branches changed.

The deployment gate should fail when:

- `s-router-prod` consumes an unpinned branch ref for the production router chain.
- `flake.lock` resolves production router-chain inputs to revisions different from the declared freeze pins.
- `s-router-prod` consumes lab source as production source.
- The freeze pins are changed without an explicit router-chain bump commit.

After the legacy replacement is stable, advance these pins only through an explicit router-chain bump.

## VM Image Update Ordering

The VM host treats the production gateway differently from disposable router
test VMs:

- `s-router-prod-vm.service` starts immediately from the last complete cached
  image; a network image build must never block gateway startup.
- `s-router-prod-image.timer` refreshes against the latest committed NixOS
  repository locks six hours after the previous refresh completed. A long build
  therefore cannot cause an immediate rebuild loop.
- The production image service is ordered before the clab, NixOS, and client
  test-router image services, so those builds cannot hold the global image lock
  while the gateway candidate is waiting.
- A successful build pins the running image, atomically selects the candidate,
  gracefully restarts the VM, and verifies that QEMU is using the candidate.
  A failed build never touches the running VM; a failed candidate start restores
  and restarts the pinned previous image.
- An unexpected production guest shutdown restarts from the last complete
  cached image; it never starts a network build in the gateway service cgroup.

The registered test routers use a different shutdown contract. A guest shutdown
runs the latest-lock image updater before systemd restarts the VM. The stop
transaction has a two-hour timeout and control-group kill semantics so a failed
or timed-out build cannot survive as an orphaned updater or lock holder.

## Target Boundaries

`s-router-prod` becomes the production replacement target for the legacy routers.

`s-tau` is the first physical canary host for `s-router-prod`.

`s-sigma` stays on the legacy router path until `s-router-prod` has passed canary checks on `s-tau`.

The committed `s-tau` state is intentionally conservative: the `eno1` carrier
watcher still controls the legacy core and edge router VMs, and
`s-router-prod` is present but has `autoStart = false`.

During an actual canary, change the carrier-controlled unit list to only
`s-router-prod-vm.service` and make sure the legacy core and edge router VMs are
not started on the same L2 domains.

The existing host bridge model should remain:

```text
eno1 -> vmbr1  # ISP / WAN L2 handoff, no host IP or DHCP
eno3 -> vmbr4  # LAN trunk
eno4 -> vmbr0  # host management
```

The `s-router-prod` VM should consume that as:

```text
eth0 -> vmbr4  # LAN trunk
eth1 -> vmbr1  # WAN / ISP handoff
```

The VM NIC MAC addresses should be pinned to the current legacy router MAC addresses. The WAN MAC is especially important because changing it can leave the ISP or upstream equipment holding the previous L2 identity long enough to cause an avoidable internet outage.

The concrete legacy MAC values are intentionally not repeated in this document.
They belong in the Nix VM definition only, where the router process actually
needs them.

The host should not learn WAN addresses and should not implement router behavior. The host only provides the L2 attachment, VM lifecycle, storage, and secrets wiring.

## Production Source Model

Create a small, explicit production model source for `s-router-prod`.

Preferred initial location:

```text
prod-network/s-router-prod/intent.nix
prod-network/s-router-prod/inventory.nix
```

The production model source must not be spread across `s-sigma`, `s-tau`, or generic NixOS host modules. Router behavior should live in the model source and flow through:

```text
intent/inventory -> compiler -> NFM -> CPM -> network-renderer-nixos -> NixOS
```

NixOS may provide host hardware attachment, VM lifecycle, secret references, and
rollback mechanics. Router behavior should flow through the renderer path where
the production model can express it. Current exceptions must be explicit,
reviewed, and temporary.

Current reservation source handling:

- VLAN 2 DHCP reservations are a temporary, explicit exception.
- The pinned CPM and renderer support a scope-level protected reservation source
  using schema `gamp-protected-reservation-set-v1`, source class `protected`,
  and a runtime source file.
- Because the real MAC addresses and `hostname` values must not be published in
  inventory, flake eval output, or the Nix store, the existing aggregate VLAN 2
  secret must be migrated and validated against that schema before the native
  contract can replace the override.
- `vlan2-kea-reservations-override.nix` mounts the existing encrypted legacy
  VLAN 2 reservation source at runtime and overwrites only
  `.Dhcp4.subnet4[0].reservations` in the renderer-generated
  `/run/etc/kea/vlan2.json`.
- The override treats reservation `hostname` as private by default. Only
  explicitly allowlisted public hostnames are copied into the runtime Kea file;
  all other reservations keep only `hw-address` and `ip-address`.
- `vlan3-kea-reservations-override.nix` remains because its existing secret is
  a raw MAC address, not a protected reservation-set document.

These overrides can be removed after migrating the secrets to the renderer's
protected reservation-set contract without exposing private identities.

Other reviewed compatibility exceptions:

- `kea-legacy-lease-paths.nix` keeps the existing lease databases directly
  below `/var/lib/kea`; removing it still makes Kea use an invalid nested
  memfile path with the current renderer.
- `ipv6.nix` owns DHCPv6-PD acquisition, PPPoE `defaultroute6`, runtime Nebula
  ingress rules, and no tenant-route compatibility layer. The pinned renderer
  derives each tenant `/64` from its delegated prefix and slot and owns those
  routes together with router advertisements.

The former Nebula public-ingress hotpatch has also been removed. The production
inventory models a dedicated VLAN 3 policy transit and the CPM/renderer chain
now emits scoped TCP/UDP 4242 DNAT, SNAT, forwarding, and forward/return routes.

The former VLAN 3 to VLAN 2 priority-900 return override has been removed. The
pinned renderer already emits the stateful firewall return, source policy rule,
main-table fallback, and VLAN 2 route; the parity contract asserts those native
outputs and rejects reintroducing the local rule.

Every active compatibility override listed by the production module emits a
NixOS evaluation warning with its reason and removal condition.

PPPoE is modeled in `inventory.nix` as a `core` PPPoE client on `wan` with
runtime interface `ppp0`. The current control-plane PPPoE service validates
client/server pairs, so production also models a non-rendered external ISP peer
to satisfy that contract without adding a hand-written NixOS PPPoE service.

The production logical units should describe the replacement router functions directly:

- `core`
- `upstream-selector`
- `policy`
- `downstream-selector`
- `access-vlan2`
- `access-vlan3`
- `access-vlan7`

Do not keep lab-style access units in the production render. `access-vlan2` replaces the legacy VLAN 2 LAN at `192.168.1.1/24`; `access-vlan7` replaces the legacy VLAN 7 LAN at `192.168.2.1/24`.

## Scaffold Strategy

Required scaffold changes:

- Use the production model source directly.
- Set the host name and renderer selector to `s-router-prod`.
- Override the VM NIC list to match the legacy router handoff: `eth0 -> vmbr4` and `eth1 -> vmbr1`.
- Pin the legacy LAN and WAN MAC addresses.
- Keep production behavior separate from lab/HAT/SIT source authority.

## Legacy Parity Comparison

The production comparison target is not the old experimental `s-router-core` host. The required comparison is:

```text
s-router-prod
  vs
s-router-legacy-core + s-router-legacy-edge
```

This matters because the current working legacy router is split across two surfaces:

- `s-router-legacy-core` owns the ISP/core side, including PPPoE.
- `s-router-legacy-edge` owns the client edge side, including client VLANs, DHCP/DNS-facing behavior, and NAT/firewall behavior.

The `s-router-prod` generated output should be compared against the combined behavior of both legacy routers.

Legacy core comparison points:

- Outer VM NICs:
  - `eth0 -> vmbr4`, pinned to the legacy LAN VM MAC.
  - `eth1 -> vmbr1`, pinned to the legacy WAN VM MAC.
- VM-internal trunks:
  - `eth0` becomes the LAN trunk.
  - `eth1` becomes the WAN trunk.
- Core container attachment:
  - legacy passes `br-lan-trunk` into the container as `lan`.
  - legacy passes `br-wan-trunk` into the container as `wan`.
- WAN VLAN:
  - legacy creates `wan.6`.
  - legacy bridges `wan.6` as `br-wan6`.
- PPPoE:
  - legacy runs PPPoE against `nic-br-wan6`.
  - legacy creates `ppp0`.
  - legacy sets `defaultroute`, `persist`, and MTU/MRU `1492`.
  - legacy consumes `/run/secrets/pppoe-username` and `/run/secrets/pppoe-password`.

Legacy edge comparison points:

- Edge container receives the LAN trunk.
- Client VLANs are materialized from the LAN trunk.
- Legacy client LANs include VLAN 2 and VLAN 7.
- DHCPv4 behavior for those client VLANs must be represented in `s-router-prod`.
- DNS or resolver behavior needed by clients must be represented in `s-router-prod`.
- NAT/firewall behavior must be represented in `s-router-prod`.

The static gate should compare attrsets and rendered artifacts, not just boot success. At minimum compare:

- `virtualisation.qemu.networkingOptions`
- `systemd.network.netdevs`
- `systemd.network.networks`
- `containers`
- PPPoE service definitions or rendered PPPoE artifacts
- nftables/NAT output
- DHCP/DNS service output

The comparison is allowed to differ structurally because `s-router-prod` should be one generated production target instead of two legacy routers. It is not allowed to differ on the ISP handoff contract, PPPoE lower interface, client gateway behavior, NAT44 behavior, or duplicate/changed MAC behavior unless the difference is explicitly intentional and tested.

## Current Functional Scope

The production target models the IPv4 behavior required to replace the legacy
routers:

- WAN PPPoE on the WAN handoff via `eth1`.
- The correct ISP VLAN on the WAN side, based on the legacy configuration.
- LAN trunk on `eth0`.
- Legacy client VLANs, starting with the smallest useful set.
- DHCPv4 for client networks that legacy currently serves.
- DNS or resolver behavior needed by clients.
- Source-scoped NAT44 toward the PPPoE interface.
- Firewall default-deny with explicit allows.
- Management reachability for recovery and debugging.

Routed IPv6 is now part of the production target. The pinned renderer owns
router advertisements and the slot-derived delegated-prefix `/64` routes. The
local IPv6 module is limited to acquiring the prefix over PPPoE, enabling the
IPv6 default route, and admitting scoped Nebula ingress.

## Static Verification Gate

Before any runtime cutover, verify the generated `s-router-prod` output without deploying it.

Required checks:

- `s-router-prod` builds from the locked graph.
- The generated artifacts exist under `network-artifacts`.
- The output does not reference lab/HAT paths.
- The QEMU NIC list maps `eth0` to `vmbr4` and `eth1` to `vmbr1`.
- The QEMU NIC list pins the legacy LAN and WAN MAC addresses, especially the WAN MAC on `vmbr1`.
- The WAN interface is attached only through the `vmbr1` VM NIC path.
- The host does not configure DHCP or IP addressing on `vmbr1`.
- The `s-router-prod` attrsets are compared against `s-router-legacy-core` and `s-router-legacy-edge`.
- The PPPoE lower-interface path is equivalent to legacy core: WAN handoff to WAN VLAN to PPPoE to `ppp0`.
- Rendered systemd-networkd output contains the expected LAN and WAN lower interfaces.
- Rendered PPPoE behavior matches the model source.
- Rendered DHCPv4 scopes match the intended legacy replacement networks.
- Rendered VLAN 2 DHCP reservations do not contain real MAC addresses or
  private `hostname` values in the Nix store; those are applied only by the
  documented runtime override. The override must keep masking deny-by-default
  and allow only explicitly public hostnames.
- Rendered NAT44 is source-scoped and points at the intended egress interface.
- Renderer-native router advertisements and delegated tenant `/64` routes match
  the production intent. No local `s-router-prod-ipv6-routes` compatibility
  services may be present; DHCPv6-PD and Nebula ingress glue remain local.
- Renderer-native public ingress includes scoped TCP/UDP 4242 DNAT, SNAT,
  forwarding, and dedicated VLAN 3 forward/return routes. No local public
  ingress hotpatch may be present.
- No unexpected hand-written nftables, routes, DHCP, DNS, or PPPoE logic is
  added in NixOS outside the renderer path.

## Canary Procedure On s-tau

Use `s-tau` as the first canary because it can become the router by moving the ISP handoff to it, while `s-sigma` can remain the rollback path.

Do not run legacy and `s-router-prod` as active gateways or DHCP servers on the same client VLAN at the same time.

Do not attach legacy and `s-router-prod` to the same L2 domains at the same time with the same pinned MAC addresses. The pinned MACs are required for continuity, but duplicate live MACs would make the canary invalid and can create confusing bridge or upstream behavior.

The canary should use one of these modes:

- Isolated test VLANs first.
- A short controlled window where legacy router service for the target VLANs is stopped before `s-router-prod` starts serving them.

Runtime checks:

- `s-router-prod` boots cleanly.
- The WAN link is visible inside the VM on the expected interface.
- PPPoE establishes successfully and starts automatically after a cold boot.
- The router receives the expected IPv4 route.
- A client receives DHCPv4 from the expected network.
- A client can resolve DNS.
- A client can reach IPv4 internet.
- NAT counters move for client traffic.
- Firewall behavior denies traffic that should not pass.
- Rebooting `s-router-prod` preserves behavior.
- Rebooting the host does not accidentally start legacy and prod routers together.
- Rollback restores the same WAN MAC immediately, without waiting for upstream MAC state to expire.

## Rollback Requirements

Rollback must be mechanical before production cutover.

Minimum rollback options:

- Stop `s-router-prod`.
- Restart the legacy router path.
- Or physically move the ISP handoff back to the known-good host.
- Confirm client DHCP, DNS, NAT, and internet reachability through the legacy path.

The rollback procedure should be documented as commands, but deployment, switch, shutdown, and reboot commands should not be run unless explicitly requested.

## Stop Conditions

Stop and fix the owning layer if any of these happen:

- Production output consumes lab/HAT source unexpectedly.
- `s-router-prod` references lab/HAT/SIT source paths.
- Renderer output requires additional hand-written NixOS routing, firewall,
  DHCP, or NAT glue beyond the reviewed DHCPv6-PD and Nebula IPv6 ingress
  integration.
- WAN and LAN NIC order is ambiguous.
- The production router does not pin the legacy WAN MAC.
- Legacy and production routers would be live on the same L2 domain with the same MAC.
- Legacy and production routers would both serve the same client VLAN.
- Runtime behavior differs from the model and the difference cannot be explained from generated artifacts.
- The PPPoE client is rendered but not enabled in the boot transaction. In that
  state the VLAN 2 nftables and route output can still look correct, but clients
  will not have internet after a cold boot because `ppp0` never comes up.

CMC fixes belong in the owning implementation repository. Do not paper over compiler, NFM, CPM, or renderer gaps with permanent NixOS-side shims.
